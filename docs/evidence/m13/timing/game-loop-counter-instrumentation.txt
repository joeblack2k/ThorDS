M13 semantic game-loop counter instrumentation
Date: 2026-08-01
Status: INSTRUMENTED_NOT_VALIDATED
Profile target: ASMP / revision 0

Source mapping:
- SM64DS decomp `func_020197b8.c` increments `data_020a0db0` once per
  iteration of the main game loop.
- The mapped address is `0x020A0DB0` in the ARM9 main RAM address space.

Implementation:
- `MelonInstance::getSm64dsGameLoopTelemetryJson()`
- `MelonDSAndroid::getSm64dsGameLoopTelemetryJson()`
- JNI `MelonEmulator.getSm64dsGameLoopTelemetry()`
- reads the existing `NDS::MainRAM` buffer without modifying emulation state;
- samples the counter after each `MelonInstance::runFrame()` call;
- reports one-second windows containing `windowWallNs`, `uniqueUpdates` and
  `emulatorFrames`, plus the latest raw `counter` and `lastDelta` for
  diagnosing address/lifecycle mismatches;
- also reports `cadenceValue`, the mapped `data_0208ee44` game-side cadence
  value, which distinguishes a 60 Hz loop from a two-tick gameplay schedule.
- emits the same aggregate window at native debug level with the stable
  `SM64DS game-loop window` marker, so a running Thor session can be sampled
  without changing pause/resume behavior.

Build evidence:
- `:app:compileGitHubProdDebugKotlin`
- `:app:assembleGitHubProdDebug`
- GitHub Prod Debug CMake/native compilation
- result: `BUILD SUCCESSFUL` (`76 actionable tasks: 9 executed, 67 up-to-date`)

Boundary:
- This is an internal read-only measurement path, not a 60fps toggle or patch.
- `uniqueUpdates` is the delta of the mapped decomp counter and is not yet
  validated against a live EU ASMP session on the Thor.
- `emulatorFrames` counts completed `NDS::RunFrame()` calls in the sampled
  window; it is diagnostic context, not presenter FPS.
- The first Thor probe produced `emulatorFrames=14` and an apparent
  `uniqueUpdates=352293278`. Raw values showed that the game reset the counter
  during launch/scene initialization; the sampler now treats a descending
  counter as a new baseline instead of a 32-bit wrap.
- The corrected probe is not promoted to a 60fps result yet: the observed
  window was interrupted by launch/pause lifecycle state and did not provide
  a stable gameplay interval.
- A later stable Castle Garden session produced windows of
  `uniqueUpdates=60/61`, `emulatorFrames=60/61` and `cadenceValue=1`.
  This confirms the native sampler is live, but it is not sufficient to claim
  60fps gameplay because timer/physics/audio semantics and the exact scene
  schedule still need comparison against a known baseline.
- It does not prove that the counter remains semantic through all scene,
  overlay, pause, transition and save/relaunch paths.
- The 60fps mode remains unimplemented and unvalidated.
